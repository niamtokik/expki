## keys

Did a quick cleanup on the module, started to write tests,
and added a way to verify the key using erlang functions.

The public key can now be generated from the private key
after it was generated. This public key should also be
stored in the database alongside the private key.

A private key can be generated using the [`genpkey`](https://man.openbsd.org/openssl#genpkey)
command. The `-text` flag wil also output all information
about the key itself (exponent, modulus and so on). The
`-pkeyopt` flag can be used to set the bit for example.

```console
$ openssl genpkey -outform pem -text -algorithm rsa -pkeyopt rsa_keygen_bits:2048
```

The public key can be extracted from the private key
with the command [`pkey`](https://man.openbsd.org/openssl#pkey)

```console
$ openssl pkey -pubout -text -outform pem
```

The full operation in one line to extract the public key
from a newly created private key:

```sh
openssl genpkey -outform pem -algorithm rsa -pkeyopt rsa_keygen_bits:2048 2>/dev/null \
    | openssl pkey -pubout -text
```

## Certificate Authority

A certificate Authority or CA is a special kind of certificate used to
sign certificate requests and produces the final certificate for an user.
A CA can be shared with other people using the PKI to verify if the
encrypted/authenticated data are valid. The key used to sign the CA
MUST BE stored in a safe place and encrypted.

A CA can also delegate its role to other CAs, but it will not be implemented
right now. Here the procedure to generate a CA with openssl


```sh
# first generate a new crt, it possible to generate the key
# at the same time
openssl req -x509 -new -nodes \
  -keyout ca.key.pem -keyform pem \
  -sha512 \
  -days 3650 \
  -utf8 \
  -pkeyopt rsa_keygen_bits:2048 \
  -out ca.pem \
  -subj '/C=CO/O=OrganizationName/OU=OrganizationalUnit/ST=State/CN=CommonName/SN=SerialNumber/'
```

* `-new`; certificate request
* `-nodes`: certificate is not encrypted
* `-x509`: X509 format used

The list of available subjects can be found in the [RFC5280](https://www.rfc-editor.org/rfc/rfc5280.txt),
and also in this [stackoverflow answer](https://www.rfc-editor.org/rfc/rfc5280.txt). They
can also be found in the [X.501](https://www.itu.int/rec/dologin_pub.asp?lang=s&id=T-REC-X.501-200508-S!!PDF-E&type=items)
specification document. It seems most of them are also defined in the [LDAPWiki](https://ldapwiki.com/wiki/Wiki.jsp?page=OrganizationalUnit).

All those elements should probably be stored in their own
table as well.
